# GitHub 公开发布

## 固定原则：无需用户反复重申

1. **公开通用代码、通用文档和可复用工作流；不公开私人 docs、实际配置、凭据或运行证据。** 用户说“公开项目”，不等于授权公开其私人资料。
2. **一个项目维护一套公开实现。** 不把完整版留在 private、把缩水副本放在 public，也不长期维护两条容易改错/推错的代码线。独立组件可以各自有公开仓库，不必为了单一实现强行改成 monorepo。
3. **个人绑定属于外置配置。** 用户名、工作目录、设备地址、SSH 信任绑定、仓库名单、会话 ID、安装位置等不得写死在通用源码里。示例使用清楚的占位符或合成数据。
4. **私人文件加入 `.gitignore`，但不能把 ignore 当成历史清除或发布过滤器。** 已跟踪文件、历史、包产物和附件需要分别处理。
5. **不默认重建历史。** 用户允许保留历史、且轻量检查没有实际问题时，保留原历史。只有发现真实敏感内容或用户明确要求时，才提出有针对性的清理方案。对某个仓库的历史许可不要扩大到其他仓库。
6. **公开内容必须能被别人独立使用。** 完整工作流不能暗中依赖私有包、作者机器上的文件、内部脚本或私人部署数据；核心库可选功能与完整工作流要如实区分。
7. **不借发布重做架构。** 优先迁移、参数化已有可用实现，保留测试和运行语义。不另造不必要的框架、审批系统、模型进程或扩展。
8. **授权按仓库和动作确定。** 已明确允许的公开操作无需重复询问；新发现的另一个私有依赖、删除远端、强推或重写历史等超出范围的动作，需要相应确认。技能不是所有未来仓库的永久发布许可。

## 1. 确定真实边界

- 确认工作目录、`git status`、远端 URL、分支、当前提交和 GitHub 当前可见性，不凭文件夹名判断。
- 列出将公开的项目/组件与用户已给的授权。区分主项目、独立依赖和机器部署。
- 识别正在运行的服务及其源码/配置位置；发布不应擅自停止业务、覆盖未提交文件或破坏已有会话。
- 使用明确的文件清单。子任务必须写明绝对工作目录；合并结果时核验文件实际落在目标仓库，不能只相信子任务报告。

## 2. 分离公开与私人内容

公开：通用源码、必要测试、安装和使用文档、通用设计说明、许可证、无个人值的配置模板。

私人：个人部署/调试记录、会话、任务数据、机器/账号清单、真实配置、SSH 材料、凭据、运行日志、恢复 journal/receipt/quarantine、业务证据和截图。

优先把私人内容放在仓库外。需留在工作目录时采用明确的私人目录或命名，并加精确 ignore 规则，例如：

```gitignore
/private/
/docs/private/
/docs/local/
/docs/*.local.md
/docs/deployment-local.md
/config.local.json
/workflow.local.json
.env
.env.*
!.env.example
/state/
*.log
```

这是约定示例，不可盲目覆盖现有 `.gitignore`。不要简单忽略所有 `docs/`，以免删除开源项目所需的通用说明；`.env.example` 等例外也必须确实不含私人值。

对已跟踪的私人文件：先备份并确认用途，用**精确路径**取消跟踪、保留本地文件，再确认 `git ls-files` 不再包含它们。不要用 `git rm -r --cached .`、批量 `git add .` 或删除全部文档代替分类。

## 3. 按风险检查历史，不制造无意义的重写

- `.gitignore` 不会删除旧提交内容。查看将暴露的分支、标签、文件历史；轻量项目先做轻量检查。
- 用户明确允许保留短历史且未发现真实敏感内容时，可以直接保留，不强制 orphan、镜像导出或拆出第二个仓库。
- 若私人文档曾被提交：指出具体文件与受影响历史，确认保留历史的许可是否包含这些内容；不能只加 ignore 就宣称文件从未公开。
- 若发现仍有效的秘密：停止相关发布，说明需撤销/轮换；删文件或改写历史不能让已泄露凭据恢复安全。
- 只有确有必要才提出历史清理；先解释受影响 refs、协作者和备份，再取得授权。不要未经确认强推。
- 不把扫描无匹配称为“绝对无秘密”。也不要因存在个人姓名、公开项目 URL 或合成测试数据就虚构凭据泄露。

## 4. 验证公开的是完整产品

- 检查源码、安装脚本、文档、测试和配置中所有个人硬编码及私有依赖。
- 私有依赖不可用时如实列为完整发布阻塞；获得授权后公开其通用部分或使用已有公开替代。不偷偷重写另一套实现。
- 用公开文件在独立目录安装/构建/运行测试；不要仅靠作者机器的 `node_modules`、私有源码或旧构建产物证明可复用。
- 验证用户承诺的完整路径，而不只检查进程存活或提交接收。分别标注模拟测试、真实 Git 测试、真实传输、实际应用和模型介入。
- 普通用户应能仅凭公开仓库、公开依赖和自己的配置运行同样的工作流。

## 5. 审查实际发布面

读取 `references/release-checklist.md`，检查：

- 当前受跟踪内容与即将提交的精确 diff。
- 保留的 Git 历史、分支和标签。
- README、示例、截图、GitHub Actions 和日志。
- npm/其他包的**实际文件列表**、release 附件、source maps、缓存和生成目录。
- GitHub 可见性改变可能公开的仓库资料（issues、releases、wiki 等），不能只看工作树。

扫描结果以文件名、类别、必要的行号报告；不要将匹配到的 token、私钥或私人文档全文打印到日志或公开证据中。自动扫描不替代语义检查。

## 6. 收敛为唯一主仓库

迁移前保留仓库外的私有离线备份，覆盖 Git refs 和未提交/未跟踪资料；验证备份可读。用户要求消除双仓库混乱时，旧 private 最终只留离线档案，而不是继续当开发入口。

在完整工作流、配置迁移、测试和发布检查通过后，统一开发目录、origin、安装入口及文档链接。运行数据和恢复证据不因源码迁移而丢弃。删除旧远端或腾出名称之前，确认准确仓库、授权和备份，避免把刚迁好的公开仓库删掉。

## 7. 发布与回读

- 已授权的可见性变更/推送可以执行，但不擅自扩展到 npm publish、其他私有依赖或仓库删除。
- 发布后从 GitHub 独立读取实际可见性、默认分支和提交，核对公开内容与审查结果。
- 不以命令 exit 0、测试数量或通知“已提交”代替公开可访问、依赖可取得和工作流可运行。
- 简短报告：唯一公开入口、已验证能力、私人资料存放与 ignore 状态、历史处理方式、仍存在的具体阻塞。不要把准备完成说成发布完成。
